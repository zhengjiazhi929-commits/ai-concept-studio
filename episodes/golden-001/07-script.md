# 第一版口播脚本 v0.1

- 标题：**Agentic Coding 到底是什么？AI 为什么开始从“写代码”变成“交付任务”？**
- 预计口播：约 10 分 30 秒～11 分钟
- 受众：AI 产品经理及技术邻近岗位
- 状态：等待人工表达审稿
- 说明：文中的 SaaS 导出功能是教学案例，不是真实产品实测

---

## 0:00–0:45｜同一句需求，两种 AI Coding

【画面】左右分屏，输入同一句话：“给后台增加一个批量导出客户的功能。”

【口播】

同样让 AI 给一个 SaaS 后台增加“批量导出客户”的功能。

左边给你一段代码，然后等你继续指挥。一个配置了代码库、执行环境和测试工具的 Coding Agent，则可以读项目、改文件、跑测试，失败后根据反馈尝试修正，最后提交一份可审查的改动。

如果还用“代码写得快不快”评价它们，你可能从一开始就看错了。Agentic Coding 真正改变的是：**谁在负责把任务向前推进。**

而这会直接改变产品的权限设计、验收方式和成功指标。

---

## 0:45–1:25｜Agentic Coding 到底是什么

【画面】代码块缩小，依次出现“环境、闭环、验收”三个图标；详细任务卡暂不展开。

【口播】

这就是今天要讲的概念：**Agentic Coding，智能体式编程。**

我们先给它一个可操作的定义。

它先接收一个目标。然后在被允许的开发环境里，连续选择和执行动作：读取代码、修改文件、调用工具，再根据执行反馈尝试修正。达到验收条件时交付结果；遇到歧义、权限边界或者无法继续的情况时，就把问题升级给人。

这里最重要的不是“自动写代码”，而是三个词：**环境、闭环、验收。**

---

## 1:25–2:15｜它和过去的 AI Coding 有什么区别

【画面】光标补全、聊天窗口、任务循环依次出现，但最后保留在同一屏幕上。

【口播】

代码补全预测下一段代码，推进任务的人是你；聊天式编程提供解释、方案或者补丁，在典型的纯聊天工作流里，落盘、运行和报错后的下一步仍由人推动；Agentic Coding 则进入开发环境，把读取、修改、执行和反馈连成循环。

三者今天仍然并存，只是 AI 承担的工作单位变大了：从代码片段，到一轮对话，再到一项任务。

顺带一句，Vibe Coding 没有统一的正式技术定义。本期只做一个工作区分：它更多描述人如何使用和验收 AI；Agentic Coding 描述系统能不能连续推进任务，两者不是一个维度。

---

## 2:15–4:00｜一项任务是怎样被推进的

【画面】同一画布连续变换：任务卡展开约束 → 拆成权限、脱敏、性能、测试四个子任务 → 进入执行闭环。

【口播】

我们回到刚才的批量导出功能。

如果只说“加个导出按钮”，这其实不是一个合格的任务。按钮能点，就算完成吗？普通用户能不能导出？手机号要不要脱敏？十万行数据会不会把页面卡死？旧功能有没有被破坏？

所以在生产场景里，更稳妥的第一步不是立刻让 Agent 动手，而是把愿望整理成一张任务合同：目标是什么，不能做什么，什么才算完成，哪些操作必须先问人。

接下来，Agent 才开始进入循环。

它先读取与任务有关的代码和项目规则，找到权限模块、客户数据模型，以及项目里原有的导出方式。

然后，它选择下一步行动。可能先改后端接口，也可能先补测试。这里不要求每个 Agent 都先写一份完整计划，关键是它能根据当前状态连续决定下一步。

再往后，它通过工具修改文件、运行测试、查看终端输出；如果配备浏览器或界面操作工具，还可以打开页面验证交互。

最关键的一步来了：这些工具返回的结果，会成为它下一轮判断的依据。也就是说，它不是靠自己的感觉宣布“应该能用”，而是让实际执行环境告诉它：刚才那一步到底产生了什么结果。

所以 Agentic Coding 的基本闭环可以压缩成一句话：

**目标 → 读取环境 → 采取行动 → 观察结果 → 修正 → 验证。**

---

## 4:00–4:50｜失败之后，它是不是只会再试一次

【画面】权限测试变红：普通用户请求仍返回成功。执行环倒带到“观察结果”，再弹出“重试 / 换方案 / 问人 / 回滚”四个出口。

【口播】

假设 Agent 写完导出接口，一跑权限测试，发现普通用户居然也能拿到数据。

普通聊天式编程里，往往需要你把报错复制回来，再问一句“这是怎么回事”。

如果日志、代码上下文和相应工具齐全，典型的 Agentic 工作流可以读取失败信息，尝试判断是测试、实现还是需求出现了问题。定位到可能原因后修改，再运行相关测试和必要的回归测试。

如果发现需求有歧义，或者反复尝试仍无法解决，它就应该停下来，把已尝试的记录和控制权交还给人。

**失败恢复，不等于无脑重试。**

---

## 4:50–6:05｜它不是一个更聪明的模型，而是一套系统

【画面】镜头从“模型大脑”向外拉，出现上下文、工具、状态、验证和控制五个模块。

【口播】

讲到这里，会出现第二个很重要的认知转折：

真正决定一个 Coding Agent 能不能进入真实工作的，往往不只是模型，而是模型外面的整套系统。

一个可进入真实工作的系统，至少要回答三个问题。

它**知道什么**？这取决于代码库、需求、团队规范和当前任务状态。

它**能做什么**？这取决于文件、终端、测试、浏览器、Git 等工具，以及环境权限。

它**怎样证明结果，又怎样受到约束**？这依靠验证规则、权限、日志、预算、审批和回滚。

负责把模型、工具和环境组织成执行循环的这一层，常被叫作 Agent Harness，也可以先把它理解成 Agent 的“编排与运行系统”。

同一个模型放进不同的上下文、工具和验证体系里，最终表现可能差很多。所以只比较底层模型跑分，并不能完整判断一个 Coding Agent 好不好用。

---

## 6:05–7:25｜自主执行，不等于无限授权

【画面】绿色、审批紫和红色三类权限闸门。具体分类标注“依团队策略配置”。

【口播】

很多人听到 Agentic，会直接把它理解成“让 AI 自己干，不要打扰我”。

但生产级的自主，恰恰要先回答：它可以在哪个范围里不用打扰人？

比如在隔离环境中读取代码、运行测试，可以设为自动允许区域；安装新依赖、扩大修改范围，可以进入需要审批的区域；数据库迁移和生产部署，则应该放进高风险区域，通常需要人工批准。具体分类由团队风险策略决定。

这就是为什么 Coding Agent 会需要文件系统和网络隔离、最小权限、操作日志、Diff 审核以及人工确认。

沙箱可以把 Agent 能接触和影响的范围变成可配置的技术边界；再配合权限、日志和审查机制，行动过程才更容易被追踪和审计。它降低风险，但不是绝对安全的保证。

如果案例中的导出功能需要数据库迁移，Agent 可以先提出方案，但执行动作应该停在预设的审批闸门前。

所以请记住：**自主性描述它能否连续推进，授权描述它被允许推进到哪里。**

---

## 7:25–8:30｜Agent 说“完成了”，为什么还不算完成

【画面】“Done”按钮被拆成六张证据卡，逐项与开头的任务合同连线。

【口播】

还记得开头那张任务合同吗？Agent 的“Done”只是一个主张，只有逐项拿出证据，才算交付。

真正可验收的交付，至少应该让人看到：改了哪些文件，普通用户是否被拒绝，敏感字段是否脱敏，大数据量是否会阻塞页面，旧功能有没有回归，以及还有哪些风险没有解决。

测试很重要，但测试通过只代表通过了现有测试。测试可能没覆盖真正的业务规则，也可能和需求本身错位。

所以“完成”不能由 Agent 自己定义，它必须回到最开始的任务合同，用代码差异、测试结果、界面行为、性能或安全检查等证据逐项证明。

这也是任务级评测与孤立代码生成评测的一个关键区别：评测对象不再只是一段代码能否生成或通过局部测试，而是系统能否在指定代码库、环境和规则下完成任务。

---

## 8:30–9:15｜什么任务最适合先交给 Coding Agent

【画面】二维矩阵：横轴“是否容易验证”，纵轴“失败影响”；不同任务作为圆点落入矩阵。

【口播】

那么，哪些任务适合优先 Agent 化？

通常是目标清楚、结果容易验证、修改可以回退、权限范围明确，而且失败影响有限的任务。比如边界明确的 Bug 修复、补测试、批量重命名、机械性重构，或者有成熟验收规则的小功能。

相反，如果产品目标还很模糊，涉及核心架构或跨团队取舍，又没有可靠测试；或者任务会接触敏感数据、生产环境和不可逆操作，就不应该默认给它很高自治权限。

自治程度不是越高越先进。最好的等级，是它带来的效率收益，能够覆盖验证、审查和潜在失败的成本。

---

## 9:15–10:15｜AI 产品经理应该问的五个问题

【画面】五张决策卡依次落下，随后收拢；右侧出现“任务完成 / 人工负担 / 成功成本”三个指标。

【口播】

所以以后再看一个 Coding Agent，不要只问“它用的是什么模型”。你可以先问五个问题：

第一，**任务单位**：它接收的是一份建议、一份补丁，还是一项完整任务？

第二，**操作范围**：它能动哪些文件、命令、网络和环境？

第三，**完成证据**：什么才算完成——测试、页面行为、性能指标、业务规则，还是人工验收？

第四，**人工闸门**：在哪些地方它必须停下来问人？

第五，**失败恢复**：出错后能不能看到日志和 Diff，能不能停止、回滚或者从检查点恢复？

衡量它时看三件事：真正完成了多少任务，给人增加了多少纠正和审查负担，每个成功任务最终花了多少成本。

---

## 10:15–10:45｜结尾

【画面】完整闭环收拢成一张任务卡，随后出现下一期关键词“Agent Skill”。

【口播】

所以下次再看到“一句话完成开发”的演示，先别急着问它用了什么模型。问清五件事：它推进什么任务、能动什么、如何证明完成、哪里必须问人、失败后怎么恢复。

谁在推进任务，谁定义完成，谁承担后果——这才是 Agentic Coding 真正的产品问题。
