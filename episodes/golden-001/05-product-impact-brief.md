# 产品影响简报

## 产品对象发生了什么变化

传统 AI Coding 产品主要优化“给出更好的代码建议或回答”。Agentic Coding 产品要优化的是“让一个任务在受控环境中推进到可验收状态”。

因此产品对象从一条回复扩展为：

```text
任务合同
+ 可用上下文与工具
+ 执行状态
+ 权限与审批
+ 失败策略
+ 完成证据
+ 人工接管和审计记录
```

模型仍然重要，但模型之外的执行系统开始直接决定产品是否可靠、可控和可交付。

## AI 产品经理的五项设计任务

### 1. 目标

- 用户交付的是模糊愿望，还是可验收任务？
- 目标、约束、非目标和停止条件是什么？
- 哪些歧义必须先向人询问？

### 2. 环境

- Agent 能看到哪些代码、文档、依赖和历史？
- 能调用哪些工具，哪些工具只读？
- 测试环境与真实环境差多远？

### 3. 循环

- 什么反馈会触发重试、换策略、回滚或升级给人？
- 如何限制执行时间、轮数和成本？
- 用户能否中途纠偏或停止？

### 4. 护栏

- 哪些动作自动允许，哪些必须审批？
- 文件、网络、密钥和外部系统如何隔离？
- 是否有完整日志、Diff、检查点和责任归属？

### 5. 验收

- “完成”由什么证明：测试、界面行为、性能、安全扫描还是业务规则？
- 谁做最终审批？
- 合并或上线后如何追踪缺陷与回滚？

可将这套框架压缩为：**目标—环境—循环—护栏—验收**。

## 自治等级（本片工作框架）

这不是行业标准，而是便于产品决策的分层：

| 等级 | Agent 可做什么 | 典型人工角色 |
|---|---|---|
| L0 建议 | 解释、建议、代码补全 | 人执行全部操作 |
| L1 补丁 | 生成可审查的文件改动 | 人运行和验证 |
| L2 隔离执行 | 在沙箱中修改、运行、测试和修复 | 人批准越界动作并验收 |
| L3 任务交付 | 完成多文件任务并提交 PR 与证据 | 人审查、纠偏、合并 |
| L4 高影响操作 | 可能部署、迁移或影响生产资源 | 必须有严格授权、双重确认与恢复机制，不宜默认开放 |

自治程度不是越高越好。价值取决于任务风险、验证成本和失败影响是否与授权等级匹配。

## 适合优先 Agent 化的任务

- 验收条件清楚；
- 结果可由测试或其他工具快速验证；
- 修改范围有限且结果可逆；
- 权限边界明确；
- 失败影响小；
- 相关文档、代码规范与运行环境对 Agent 可见。

## 不宜直接放权的任务

- 产品目标本身尚未明确；
- 涉及核心架构、合规或跨团队取舍；
- 缺少可靠测试或真实反馈通道；
- 涉及敏感数据、生产部署或不可逆操作；
- 高度依赖尚未显性化的组织知识；
- 即使出错也很难被快速发现。

## 应衡量什么

不要把生成代码量当成核心结果。建议指标分为五组：

| 目标 | 建议指标 |
|---|---|
| 任务结果 | 可验证任务完成率、首次验收通过率、从需求到可合并改动的时间 |
| 人工负担 | 人工纠正次数、接管率、审查时长、被拒绝改动比例 |
| 质量 | 合并后缺陷逃逸率、回归率、需求遗漏率 |
| 风险 | 越权尝试、高风险审批次数、安全扫描问题、回滚次数 |
| 经济性 | 每个成功任务的模型与执行成本、无效重试成本、CI 与环境成本 |

单个 benchmark 只能提供受控信号。采购或设计产品时，应在自己的任务、仓库、权限和验收规则上评测整套“模型 + harness + 工具 + 环境”。

## 本期给产品经理的最终判断

> 不要只问“这个模型会不会写代码”，而要问：它能否在我们允许的边界里推进任务，遇到失败能否正确处理，并用我们认可的证据证明完成。

## 不应做出的产品承诺

- “全自动完成任何开发任务”；
- “测试通过即可安全上线”；
- “开启沙箱即可消除风险”；
- “模型榜单更高就一定交付更好”；
- “减少人工步骤就一定提高效率”；
- “所有任务都应该提升到更高自治等级”。
