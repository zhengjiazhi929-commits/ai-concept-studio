## 01｜Stateless MCP

### 一句话定义

MCP 的核心通信从依赖协议级会话，转向让每次请求尽量自包含；服务器因此更容易被普通负载均衡器横向扩展。

### 为什么现在值得讲

MCP 官方在 2026-07-28 发布新版规范。新版移除原有的 `initialize` 握手和协议级 Session，并增加发现、扩展与多轮交互相关能力。GitHub MCP Server 的官方说明还给出了具体工程影响：减少会话存储依赖和部分数据库读取。

### 这条视频真正要回答的问题

- 为什么一个 Agent 协议会主动删除 Session？
- “无状态”是否等于 Agent 不再需要记忆和上下文？
- 状态从协议层移走后，应该由客户端、业务系统还是扩展层负责？
- 对扩容、故障恢复、鉴权和兼容性分别有什么影响？
- 已经接入 MCP 的产品是否需要立刻迁移？

### 推荐叙事

1. 用“为什么 MCP 要砍掉 Session”制造认知冲突；
2. 先画旧架构：初始化、会话、粘性路由、共享 Session 存储；
3. 再画新架构：请求自包含、普通负载均衡、任意实例处理；
4. 解释“协议无状态”和“业务没有状态”不是一回事；
5. 落到产品决策：谁保管上下文、怎么做版本兼容、何时迁移；
6. 用一个三实例 MCP Server 的扩容案例收束。

### 画面潜力

- 有状态与无状态请求的左右对比；
- Session 丢失导致请求失败的小剧场；
- 负载均衡器把连续请求分发到不同实例；
- “协议状态 / 任务状态 / 用户记忆”三层拆分图；
- 旧版与新版迁移清单。

### 必须守住的边界

- 不能说“MCP 或 Agent 从此没有任何状态”；
- 应表述为“协议核心趋向无状态”，应用仍可能维护任务、用户和业务状态；
- 不能把规范发布等同于所有 SDK、服务器和客户端已经完成升级；
- 成片前再次核对 SDK 支持度和版本兼容说明。

## 02｜Diffusion Language Model

### 一句话定义

扩散语言模型不是永远按“下一个 Token”从左到右生成，而是先得到一块带噪或被遮盖的文本，再通过多轮并行去噪逐步还原结果。

### 为什么现在值得讲

Google 在 2026-06-10 更新 DiffusionGemma，将扩散式文本生成带入一个公开、可试验的模型系列。它让“语言模型是否必须逐 Token 生成”从研究问题变成产品团队可以验证的架构选项。

### 这条视频真正要回答的问题

- 自回归模型为什么通常一个 Token 接一个 Token 地写？
- 扩散模型怎样在一块文本画布上并行修改？
- 它为什么可能降低单用户等待感，却不一定提升高并发吞吐？
- 哪些产品形态最可能受益：本地助手、实时改写、代码补全还是普通聊天？
- 它会替代自回归大模型吗？

### 推荐叙事

1. 同屏展示“打字机”和“整块文本逐渐显影”；
2. 用 256 Token 画布解释遮盖、预测、重新遮盖与迭代去噪；
3. 对比自回归与扩散式生成的数据依赖；
4. 解释单请求延迟、批处理吞吐和硬件利用之间的取舍；
5. 用三种产品场景做选型，而不是下“谁会取代谁”的结论。

### 产品经理应带走的决策

- 不只看 Tokens/s，还要测首屏可用时间、编辑稳定性和并发下的总成本；
- 交互式改写与局部编辑可能比纯聊天更适配扩散机制；
- 产品原型需要分别测试单用户体验和高并发服务效率；
- 新机制带来的优势高度依赖模型、硬件和实现，不能只引用厂商峰值。

### 必须守住的边界

- DiffusionGemma 仍属于实验性、早期路线；
- “并行生成”不等于所有场景都更快或更便宜；
- 不把厂商特定测试结果外推为整个扩散语言模型类别的普遍结论；
- 不宣称自回归模型即将被全面替代。

### 一手来源

- [Google AI：DiffusionGemma 概览](https://ai.google.dev/gemma/docs/diffusiongemma)
- [Google AI：DiffusionGemma 工作机制](https://ai.google.dev/gemma/docs/diffusiongemma/explained)
- [Google DeepMind：DiffusionGemma](https://deepmind.google/models/gemma/diffusiongemma/)

## 03｜Harness Engineering

### 一句话定义

Harness 是包围在大模型外部的执行与控制系统：它负责规划循环、工具调用、状态、权限、重试、验证、人工审批和可观测性，让模型不必靠提示词“自觉地”稳定工作。

### 为什么现在值得讲

IBM CUGA 在 2026-06-23 开源了较完整的 Agent Harness；7 月的新论文又用“从 Prompt 到 Contract”概括这一工程趋势。它不是突然出现的一项单点技术，而是正在形成的生产级 Agent 架构范式。

### 这条视频真正要回答的问题

- 为什么 Demo 里的 Agent 很聪明，上线后却经常不可靠？
- 哪些行为应该交给模型，哪些应该写进确定性的代码和规则？
- Prompt、Workflow、Framework 与 Harness 有什么区别？
- 为什么模型能力提升后，Harness 反而会更重要？
- 一个可审计 Agent 最少要有哪些控制部件？

### 推荐叙事

1. 用“模型是发动机，但产品还缺整辆车”切入；
2. 展示只有 Prompt 的执行链为何脆弱；
3. 将 Harness 拆成状态、工具、策略、校验、审批、评测六个模块；
4. 对比“希望模型遵守”与“系统强制执行”；
5. 用一个内容生产 Agent 演示事实闸门、脚本审批和失败重试；
6. 给 AI 产品经理一张 Harness 最小清单。

### 产品经理应带走的决策

- 高风险约束进入权限、Schema、Validator 和审批流，不只写在 Prompt 中；
- 用任务成功率、失败类型和恢复成本评估整套系统，而不是只测模型回答；
- 把模型当作可替换组件，避免业务逻辑完全耦合在提示词里；
- 明确什么步骤可自动、什么步骤必须有人负责。

### 必须守住的边界

- “Harness Engineering”尚不是定义完全统一的行业标准；
- 不应包装成替代 Prompt Engineering，而应解释为生产系统的上层工程；
- 个别框架的设计不能代表唯一正确架构。

### 一手来源

- [IBM Research：CUGA Agent Harness](https://huggingface.co/blog/ibm-research/cuga-apps)
- [CUGA 官方代码仓库](https://github.com/cuga-project/cuga-agent)
- [论文：From Prompts to Contracts](https://arxiv.org/abs/2607.08028)
- [OpenAI Presence：生产级 Agent 生命周期案例](https://openai.com/index/introducing-openai-presence/)

## 04｜AgentWorld：为 Agent 模拟一个可训练的世界

### 一句话定义

AgentWorld 模型不直接替 Agent 完成任务，而是模拟工具、网页、终端或操作系统在某个动作之后会变成什么状态，让 Agent 可以在可控环境中训练和测试。

### 为什么现在值得讲

Qwen 团队在 2026-06-24 发布 Qwen-AgentWorld 和 AgentWorldBench，覆盖 MCP、搜索、终端、软件工程、Android、Web 与操作系统等环境。它提供了一个很有差异化的新视角：Agent 竞争不只是“更强的大脑”，也可能是“更好的训练世界”。

### 这条视频真正要回答的问题

- 为什么真实网页、API 和操作系统不是理想的训练场？
- 环境模型与普通沙箱、Mock API、数字孪生有什么区别？
- 它如何根据动作预测下一个环境状态？
- 团队能否用它生成故障、做回归测试和验证危险操作？
- 模拟环境里表现好，为什么不保证真实世界也可靠？

### 推荐叙事

1. 用“教自动驾驶需要模拟城市，训练 Agent 是否也需要模拟互联网”切入；
2. 画出 Agent—动作—环境状态—反馈循环；
3. 对比真实环境测试与模拟环境测试的成本和风险；
4. 演示登录失败、接口超时、按钮变化等故障场景；
5. 落到产品团队的评测集、上线门槛和回归测试；
6. 以“世界模型不是现实世界”说明迁移差距。

### 产品经理应带走的决策

- 把环境和失败场景纳入 Agent 测试资产，而不是只存 Prompt 测试题；
- 上线前可以在模拟环境反复测试权限、异常和恢复路径；
- 真实环境仍需小流量验证，不能完全由模拟结果替代；
- 未来 Agent 平台的护城河可能包含环境数据和可复现评测。

### 必须守住的边界

- 这是较新的研究与开源系统，不是已经普遍采用的行业基础设施；
- 必须说明 simulation-to-reality gap；
- 不把“预测下一个状态”说成能完整复制真实互联网。

### 一手来源

- [Qwen-AgentWorld 官方仓库](https://github.com/QwenLM/Qwen-AgentWorld)
- [Qwen-AgentWorld 论文](https://arxiv.org/abs/2606.24597)

## 05｜Model Routing：从“挑模型”变成多目标系统优化

### 一句话定义

生产级模型路由不只是判断问题难不难，再选一个便宜或昂贵的模型；它需要同时考虑质量、延迟、缓存、合规、端点负载、失败概率和整条 Agent 轨迹的总成本。

### 为什么现在值得讲

2026-07-15 的 IBM Research 工程分析将模型路由重新描述为动态、多目标的系统优化问题。这个概念本身并非刚刚诞生，但当前多模型 Agent 架构让它从“省一点 API 费”变成核心产品能力。

### 这条视频真正要回答的问题

- 为什么最便宜的模型有时造成更高的最终成本？
- 一次调用价格与一次任务成功的总成本有什么区别？
- 路由应该只发生在任务开始前，还是在 Agent 执行中动态变化？
- 缓存、上下文长度、失败重试和人工接管怎样进入路由决策？
- 产品早期是否值得自研路由系统？

### 推荐叙事

1. 用“0.1 元模型为什么最后花了 1 元”切入；
2. 展示便宜模型失败、重试、上下文膨胀和人工接管的成本链；
3. 将路由目标拆成质量、价格、延迟、合规和基础设施五个维度；
4. 解释静态规则、分类器和执行中动态路由三种层级；
5. 给出按业务风险分层的最小路由方案；
6. 以“每个成功任务的总成本”替代“每百万 Token 价格”收束。

### 产品经理应带走的决策

- 核心指标应是 cost per successful task，而不只是模型单价；
- 高风险、强时效和可降级任务需要不同路由策略；
- 记录失败类型、重试次数、缓存命中和人工接管，才能训练或优化路由；
- 数据驻留和权限约束应先过滤可用模型，再做价格与质量优化。

### 必须守住的边界

- Model Routing 不是 2026 年才出现的新概念；
- 新的是多模型 Agent 场景下更系统的目标定义和动态决策方式；
- IBM 的工程观察不能被说成整个行业的统一结论。

### 一手来源

- [IBM Research：Model routing is simple until it isn't](https://huggingface.co/blog/ibm-research/model-routing-is-simple-until-it-isnt)

## 竞争内容判断说明

本轮的“中文内容空位”来自公开搜索结果的初筛，不等于完整的抖音竞品审计：

- Agent Skills 和 Computer Use 已出现大量中文教程与快讯，不适合作为第一条差异化样例；
- Diffusion Language Model、AgentWorld 和新 MCP 规范的系统解释内容明显较少；
- 目前还没有用户确认的“重点博主观察名单”，因此不能把公开搜索近似成对指定博主的完整监测。

在趋势 Agent 上线前，建议先建立 15–30 个重点账号的人工观察名单，只记录公开视频的标题、发布日期、点赞评论量级、讲解角度和内容缺口；不做未经授权的批量抓取。
